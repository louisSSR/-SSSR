## 原版与安全桥的能力差异

| 能力 | 原版 1.2.5 | 已审计的 1.2.5-shiro.1 |
| --- | --- | --- |
| 商店独立主题、开关与 Q 版白 | 可用；以实际宿主验收为准 | 可用 |
| 商店本源账本、任务及 AI 摘要 | 由商店保存，与数据库写入能力分离 | 相同 |
| 原生主题 JSON 和表格文件手动导入 | 可使用原生导入入口 | 相同 |
| 商店自动写入原生六表 | 暂停；公开 CRUD 缺少可靠的聊天绑定提交边界 | 仅在严格识别已审计安全桥后启用 |
| 数据库官方更新 | 按官方安装来源及更新方式操作；不代表自动更新已开启 | 本地补丁构建不能冒充官方可更新目录 |

原版 `AutoCardUpdaterAPI` 公开了 CRUD、SQL、模板、导出及模型调用等能力；`AutoCardUpdaterV2API` 公开了可视化界面的打开与刷新。它们没有公开同一运行实例的聊天绑定事务、回放基线和提交锁。单纯在 CRUD 调用前后判断聊天不能消除其内部异步等待后的写入竞态。

安全桥识别同时要求 `acu-chat-bound-projection/1` 和已核验补丁版本。桥通过原生一致性基线、事务锁、回放和提交链整批投影六表；保存目的地与请求数据在异步请求前固定，并核验服务器回读。它不声称与宿主所有其他写者具备服务器 CAS：宿主保存端点没有这种协议。代码和实测边界详见 [上游接口契约](./upstream-contract.md)。

把这些内部模块复制到外置 sidecar 会产生另一套模块状态和锁；原版不能共享它们。直接写原生消息帧、拦截 `saveChat`、包装不安全 CRUD 或靠禁止点击遮盖竞态，都不是本次采用的更新兼容方案。未来若上游公开等价安全协议，应重新审计、测试并明确支持版本；能力不存在或版本未知时保持原生自动写入关闭，仍可导出数据。

## 更新时保护数据

商店升级与数据库更新是独立动作。主题仅依赖外观适配；数据库 DOM 变化时可以关闭主题，不应让外观失败影响本源账本。更新后核验开关、手机布局、数据库编辑与保存；旧主题应能完全撤除。未来数据库改版的外观需再次测试，不能预先承诺全兼容。

从早期补丁版恢复官方版之前，应备份商店账本 JSON、相关聊天及元数据、数据库原生导出或检查点、整个数据库扩展目录和需要保留的设置。确认当前扩展目录的清单、实际 Git 根、远端和 `git status --short`。若原官方 Git 目录有本地修改，先保存差异及未跟踪文件，再决定恢复方式；不要直接运行 `git reset --hard`、`git clean` 或覆盖未知文件。

若当前是无 `.git` 的补丁复制目录，先停用并将完整备份移至酒馆扩展自动扫描目录之外，再按官方来源恢复或安装。不要同时启用两套数据库：它们有单实例启动标记且共享宿主状态。恢复后核对既有表 UID、行和数值，确认聊天可正常读写；原版不提供本补丁安全桥，商店应显示自动同步暂停。此说明没有在用户现用酒馆执行恢复操作。

## 四类 AI 记忆与原生六表

四类 AI 视图为“重要印象”“点数”“消费与购买所得”“连锁反应与任务”。它们从同一本源账本挑选有限摘要，不建立第二个余额来源。完整历史留在账本与备份，摘要只包含必要余额、相关印象、可用资产、近期交易、当前世界未解决余波和有效任务，并注明被省略的历史数量。

现有原生六表桥 v1 严格要求六张表、所有权标记和固定列头（前三列为 `row_id`、`记录ID`、`本源账户`）。不能把六张物理表直接改成四张后继续宣称兼容。当前最小方案是保留原生六表历史，用四类逻辑视图向 AI 提供限量记忆。商店继续使用唯一的 `shiro-butterfly-shop` 提示注入标识替换旧摘要；原生表的 `exportConfig.enabled` 和 `injectIntoWorldbook` 默认关闭，避免重复注入。

若以后要求四张物理原生表，必须另定模板与桥协议版本，明确迁移映射、稳定记录 ID、旧六表归档和恢复步骤，再做迁移测试。AI 摘要上限与完整历史保留是不同约束；不能通过删除历史来控制 token，也不能把字符估算声称为精确 token 数。
